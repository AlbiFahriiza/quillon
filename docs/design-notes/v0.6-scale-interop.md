# Design note v0.6 — Scale & Interop

Date: 2026-11-19 · Scope source: `myquillonplan.md` §12 v0.6, F11–F13;
research/D §5 (OTIO: parse the JSON subset ourselves, "best effort,
subset"), research/F §1 (mail-merge: name, numbers, assets per row),
research/E §2 (hwencode: vainfo-style probing, clean explicit software
fallback, hw marked non-deterministic for pixel hashes), research/B
(ffmpeg-next is the libav binding; hwencode via libav hwaccel for now).
Owner: build agent, Panoptes protocol.

## 1. Task, scope, acceptance

Scope (plan §12 v0.6, verbatim): feature `libav` (ffmpeg-next
in-process), probe & use hwencode via sidecar (`h264_vaapi`/NVENC,
vainfo-style detection + explicit software fallback), distributed render
(chunk curve), `--data` template batch (F12), OTIO subset import.

Acceptance criteria (plan §12 v0.6), each proven by a real command:

1. **1000 videos from a template + CSV complete with a shared template
   cache (identical static frames rendered only once).** Command:
   `quillon render template.json --data rows.csv -o 'out/{{name}}.mp4'`
   with 1000 rows; the `--json` summary reports cache hits proving the
   static scene's frames were rendered once and reused for the other 999
   rows. A smaller CLI test (25 rows) runs in CI.
2. **An OTIO subset document imports into a Quillon timeline with
   correct source ranges.** Command: `quillon otio import
   timeline.otio -o doc.json`, then `quillon validate doc.json` and a
   tick-level check that each clip's `source_range` and scene duration
   match the OTIO RationalTimes.
3. **libav mode produces frame hashes identical to sidecar mode.**
   NOT VERIFIABLE IN THIS ENVIRONMENT — see D5. The session delivers
   the sidecar half (which exists and is golden-tested) and records the
   libav half as a documented deviation with the exact reason and the
   CI recipe that would verify it.

Non-goals (this phase): OTIO effects/transitions/markers (flat
Timeline→Stack→Track→Clip subset only, per research/D §5); writing a
full distributed scheduler (the shareable content-addressed cache
layout that research/H requires is already in place and is *proven* by
acceptance 1's shared-cache numbers; worker fleet claiming chunks is a
v1.x concern); changing the MCP surface (templates flow through
validate/render as documents); new external dependencies (CSV and OTIO
are parsed in-tree — zero new crates).

## 2. Design decisions

D1 — Typed template variables live in the document as data (F12). An
optional `variables: BTreeMap<String, VariableDef>` field on Document
(additive; `v` stays 1, same reasoning as v0.5's D2).
`VariableDef { r#type: string|number|color|asset, default: String }`.
Substitution happens on the JSON tree *before* validation: every string
in the document (and in the `--out` pattern) interpolates `{{name}}`
markers; the result is then validated by the full pipeline, so a bad
value surfaces as a normal JSON-pointer error and the P1 contract
(document-first, validated) is never bypassed. Type checking happens at
substitution time: `number` rows must parse as f64, `color` rows as
#rrggbb, `asset` rows non-empty; unknown markers and missing columns are
errors naming the variable and the row. Asset variables may introduce
new asset entries (mail-merge per-row images): if `{{var}}` fills an
asset `src`, the row value is used verbatim and validation probes it
like any asset.

D2 — `--data` is a render-time batch, not a document mutation. `quillon
render doc.json --data rows.csv -o 'out/{{name}}.mp4'` parses the CSV
(own RFC-4180-minimal parser: quoted fields, commas, CRLF, no new
dependency), substitutes per row, validates per row, renders per row
through ONE shared frame-cache session, and reports `--json`
`{rows, outputs, cache:{hits,misses,inserts}}`. The first failing row
stops the batch with `row N:` context (fail loudly, never skip). Static
scenes are shared across rows by the existing content-addressed frame
keys — no new mechanism: scene-subtree keys already make identical
subtrees hit, which is exactly acceptance 1's "identical static frames
rendered once".

D3 — OTIO import parses the JSON subset ourselves in core (research/D
§5, option (b)). `quillon otio import timeline.otio -o doc.json
[--media-dir dir]` reads Timeline.1 → Stack.1 → Track.1(kind=Video)
→ Clip.1 with ExternalReference.1 `target_url` and TimeRange.1
`source_range` (RationalTime.1 `{rate, value}`). Mapping: fps comes
from the clip rates (must be a Quillon-legal fps; otherwise a named
error suggesting the closest legal rate); each video clip becomes one
scene holding one video element whose `source_range` is
`round(value × timebase / rate)` ticks; scene duration is the clip
duration; the first video track wins (extra tracks are a named warning,
not an error — flat subset, documented); Audio-kind tracks map to audio
tracks. `file://` URLs are stripped to paths; relative paths resolve
against `--media-dir` (default: the .otio file's directory). The output
document must pass `validate` — including the asset probe — before it
is written (import that produces an invalid document exits 2). OTIO
export is stretch scope this phase (recorded; not promised).

D4 — Hardware encode is a sidecar adapter with explicit fallback
(research/E §2). `quillon render --encode <mode>`: `software` (default,
`libx264` — pinned explicitly instead of ffmpeg's default, so renders
are reproducible), `auto` (probe `ffmpeg -hide_banner -encoders`, prefer
`h264_vaapi` then `h264_nvenc`, fall back to software WITH a printed
note), or an explicit encoder name (e.g. `h264_vaapi`) which errors
listing the encoders ffmpeg actually offers when unavailable — never a
silent fallback. Probe results are cached per render run. Hardware
encoders affect encoded bytes only (frame RGBA stays the deterministic
golden-tested path); `--json` marks `hw_encode: true|false` so
downstream tools know pixel-hash guarantees do not cover the encode.

D5 — libav is a documented deviation, not an unverified claim. The
build environment has no libav development headers (pkg-config finds
none of libavcodec/libavformat/libavutil/libswscale; no sudo to install
them), so ffmpeg-next cannot compile here. Writing a feature that has
never been compiled would violate the protocol's core rule (generated
code is a claim to verify; "should work" is banned). What this phase
delivers instead: the sidecar mode stays the verified default (F11),
the `MediaSource` contract stays libav-ready, and this note records the
exact follow-up recipe — `apt-get install libavcodec-dev
libavformat-dev libavutil-dev libswscale-dev` + a CI job
`cargo check -p quillon-media --features libav` — as the acceptance-3
verification path. The final report carries this as the single open
deviation with its reason, not as done work.

D6 — Distributed render = cache-layout proof, not a scheduler. Plan
§12's "render terdistribusi (chunk curve)" is, at v0.x, the
requirement research/H states: stateless workers over a shared
content-addressed cache, no machine-local state in keys. Acceptance 1's
1000-row run with shared cache hits is that proof rendered in numbers.
Worker orchestration itself is v1.x (plan §12 v1.x wording) and is not
built here.

## 3. Layers and dependency direction

- `quillon-core`: `variables` model + `apply_template_json` (JSON-tree
  substitution) + OTIO subset parser. No new dependencies (core stays
  internal-dependency-free).
- `quillon-cli`: CSV parser, `render --data`, `otio import` command,
  `--encode` modes + encoder probing. Reuses core's substitution and
  OTIO parser; no new dependencies.
- `quillon-media`/`render`/`cache`: untouched except no changes needed
  (cache keys already provide D2's sharing; hwencode only changes the
  ffmpeg-sidecar encode args inside `render_doc`).
- arch_gate config is unchanged (the v0.5 layer set already covers
  every edge this phase adds).

## 4. Steps, checkpoints, verification

Each step: battery (`fmt --check`, `clippy -D warnings`, `test
--workspace`), commit, push. Mid-build verification is the battery at
every checkpoint, read.

1. Core: `VariableDef`/`VariableType` model, `apply_template_json`
   (typed substitution, unknown-variable and bad-type errors, out
   pattern reuse), schema regen, boundary tests (typed values, inline
   vs whole-value markers, error pointers).
2. CLI: CSV parser (quoted/CRLF/comma), `render --data` with shared
   cache session + `--json` summary, 25-row integration test asserting
   cache hits for the static scene and misses for the variable scene.
3. Core+CLI: OTIO subset parser (Timeline/Stack/Track/Clip/
   ExternalReference/TimeRange/RationalTime) + `quillon otio import` +
   fixture timeline + tests (rate→fps legality, source_range ticks,
   media-dir resolution, invalid-OTIO named errors).
4. CLI: `--encode software|auto|<name>` + probe (parse `-encoders`
   output; explicit-unavailable error; `auto` fallback note; `--json`
   hw_encode flag) + tests with a fixture encoder list and the real
   ffmpeg on PATH.
5. Docs: README (template/OTIO/--encode sections), AGENTS.md v0.6
   surface, skills/quillon templates section, NOTICE (no new deps —
   statement only).
6. Final verification: acceptance commands (1000-row run with cache
   proof, OTIO import + validate + range checks, `--encode auto` real
   run), full battery, gates (check_diff, arch, stop), coverage via
   cargo-llvm-cov (also closing v0.5's open coverage item), CI poll,
   evidence bundle, this report's successor.

## 5. Rollback

`variables` and the OTIO/CSV code are additive: no existing field,
command, or golden hash changes (substitution only runs with `--data`;
`otio import` is a new subcommand; `--encode` defaults to today's
behavior with the encoder pinned explicitly). The golden corpus is
untouched — templates render through the same `render_tick`. Reverting
any step commit reverts its feature whole; no migration exists to undo.
